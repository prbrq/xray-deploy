# Roadmap

## Цель

Сделать `xray-deploy` понятным и безопасным в повседневном использовании, сохранив текущую техническую модель: одноразовый deploy, VLESS + RAW/TCP + `xtls-rprx-vision` + REALITY на `443/tcp`, закреплённый образ и отсутствие автоматических обновлений.

Приоритеты не привязаны к датам: следующий этап начинается после проверки и принятия предыдущего.

## P0 — Понятный первый запуск

**Статус: Завершён.**

**Проблема:** успешное развёртывание требует от пользователя понимания требований VPS, выбора REALITY target и действий после установки.

- Перестроить README вокруг сценариев: подготовить VPS, установить, получить профиль, проверить работу, устранить типовую проблему.
- Добавить короткий pre-flight checklist: поддерживаемая ОС, запуск через `sudo`, Docker, открытый `443/tcp`, готовность выбрать REALITY target.
- Описать правила выбора REALITY target и причины, по которым TLS-проверка может не пройти.
- Сделать сообщения `bootstrap.sh` более ориентированными на пользователя: показывать этапы и безопасное итоговое резюме без UUID, ключей и URI.
- После успешного bootstrap выводить краткую памятку: как снова получить URI, посмотреть логи и применить локальные изменения.
- Дополнить FAQ: отсутствие `git pull`, повторный bootstrap, размещение секретов и ответственность за firewall VPS/провайдера.

**Критерий готовности:** новый пользователь может развернуть сервер по README и понимает следующие шаги, не обращаясь к исходному коду. Окончательное принятие — после проверки на новом VPS.

## P1 — Отдельные профили доступа

**Проблема:** сейчас конфигурация создаёт один VLESS-профиль, поэтому нельзя безопасно выдать или отозвать доступ у отдельного человека.

- Поддержать несколько именованных профилей: например, «Семья» и «Друзья».
- Генерировать уникальный UUID для каждого профиля; у каждого будет собственный импортируемый VLESS URI.
- Предоставить понятные операции добавления, списка, вывода URI и отзыва профиля.
- При отзыве удалять только UUID выбранного профиля, не затрагивая остальных пользователей и REALITY credentials.
- Хранить реестр профилей локально с правами `0600`; не включать его, `.env`, `config.json` или URI в Git.
- Сохранить совместимость с существующим одиночным профилем и переиспользование credentials при повторном bootstrap.

**Критерий готовности:** владелец VPS может выдать разные URI семье и друзьям, а затем отозвать один доступ без redeploy остальных клиентов.

## P2 — Простая эксплуатация и восстановление

- Добавить в README раздел «Обычные операции»: статус контейнера, логи, получение профиля, смена fingerprint, применение конфигурации, остановка и запуск.
- Описать последовательность диагностики недоступности: firewall, TCP/443, состояние контейнера, логи, актуальность URI и fingerprint.
- Улучшить сообщения об ошибках скриптов: указывать возможную причину и безопасное следующее действие.
- Сформировать короткую памятку по резервному хранению URI и credentials без публикации их в Git, чатах или логах.

**Критерий готовности:** типовую проблему подключения можно локализовать по документации без передачи секретов третьим лицам.

## P3 — Дополнительные удобства

Реализовывать только после P0–P2 и отдельного согласования.

- Команда диагностического отчёта без секретов: состояние Compose, контейнера и слушателя TCP/443.
- Команда безопасного краткого статуса конфигурации.
- Явное создание QR-кода VLESS URI по запросу пользователя; не выводить его автоматически, чтобы не раскрывать credential на экране, в терминальной истории или записи сессии.

## Границы проекта

- Не менять без отдельного решения протокол, транспорт, flow, REALITY и порт `443/tcp`.
- Не менять закреплённый digest образа без согласованного обновления конфигурации и документации.
- Не добавлять автоматический выбор REALITY target, автоматические обновления или workflow `git pull` на развернутом VPS.
- Не ослаблять права `0600`, read-only mount конфигурации или запуск Xray без root внутри контейнера.
